# LIFT Philly i18n Simplification Plan
## Branch: i18n-simplify (from main)

## Context

Translations for 3 languages (es, vi, zh) across ~7 pages, produced by human translators.
No existing workflow. Existing translated pages are outdated and several pages are missing.

Problems with the previous approach (i18n-data-attributes branch):
- Manual annotation was tedious
- No mechanism to tell translators what is new vs already translated
- Complex JSON structure without a clear handoff format

Goal: A structured, translator-friendly workflow where it is always obvious what needs
translation and updates are easy to hand off and receive back.

---

## Design: data-i18n + CSV Export/Import

### Core Principle
English HTML is the structural source of truth. Translation data lives in JSON
(one file per page per language). Translators work from a CSV, never touching HTML or JSON.

### Workflow

1. Edit English copy in index.html (or any page)
2. node scripts/extract-translations.js --page=index
   Writes translations/en/index.json (synced from HTML)
3. node scripts/export-translations.js --page=index
   Writes translations/export/index.csv
   Columns: key | en | es | zh | vi | status
   Status: new / changed / ok  (compared to last git commit of en/)
4. Send CSV to translator -- they fill in their language column only
5. node scripts/import-translations.js --page=index --lang=es --file=index-es.csv
   Updates translations/es/index.json (upsert, does not touch untouched keys)
6. node scripts/generate-translations-new.js --lang=es --page=index
   Outputs es/index.html

### Status Tracking
export-translations.js compares translations/en/{page}.json against
git show HEAD:translations/en/{page}.json. Keys that are new or changed
get flagged. Translators only need to fill flagged rows.

### Nav/Footer
build-nav.js already injects nav/footer from _includes/nav.html and
_includes/footer.html. Add data-i18n attributes there instead of duplicating
in every page. Extractor picks them up as common keys (or a separate nav.json).
